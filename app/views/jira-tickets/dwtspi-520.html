Jira ticket DWTSPI-520

Publish upcoming API changes on their own page

Clickable prototype: Existing docs 1, Upcoming API changes. This is also the design reference.

Files for developers

  • upcoming-changes.md (new page for docs/)
  • css-additions.css (add to extra.css)
  • api-specification-changes.md (edits to the API specification page and mkdocs.yml)

User story

As a software provider integrating with the Receipt of Waste API,
I want to see upcoming API changes in one place, with their dates and what I need to do,
so that I can plan my work and avoid my integration breaking.

Context

Upcoming changes are currently a section on the API specification page, between the specification links and the change log. This story moves them to a new “Upcoming API changes” page, linked from the left-hand navigation and from the API specification page.

Each change is one entry with a type, status, a date for each environment, who it affects and what to do. The reason for the change is that the current section has no consistent structure, and does not say whether a change is breaking.

Components and patterns

  • Tag: GOV.UK Design System. Used on the new page for Breaking and Non-breaking. Guidance: Tag. Material for MkDocs has no tag colours, so the govuk-tag CSS is added to extra.css. No JavaScript.

Design acceptance criteria

Upcoming API changes page

  1. D1. The page has the H1 “Upcoming API changes”, then an introduction and a link to the Receipt of Waste API changelog.
  2. D2. Each change is an H2, followed by these lines in this order: Type, Status, Test environment date, Production environment date, Affects.
  3. D3. Type is shown as a tag: green-shade-50 text on green-tint-80 for Non-breaking, and orange-shade-50 text on orange-tint-80 for Breaking.
  4. D4. After those lines, a short description, then an H3 “What you need to do”. A change can also have an H3 “Known issue”.
  5. D5. The page ends with a link to the changelog and “Page last updated on” with a date.
  6. D6. Each H2 has 2.8em of space above it. This applies to every H2 in the documentation.

API specification page

  1. D7. The “Recent and Upcoming Changes” section is removed.
  2. D8. The first line under “API Change Log” links to the upcoming API changes page.

Navigation

  1. D9. “Upcoming API changes” is in the left-hand navigation, after the API specification page.
  2. D10. The pages match the design reference.

Acceptance criteria

  1. Given a user is on the API specification page, when they select the link under API Change Log, then they go to the upcoming API changes page.
  2. Given a user is on any documentation page, when they select “Upcoming API changes” in the left-hand navigation, then they go to that page and it is shown as the current page.
  3. Given a user is on the upcoming API changes page, when they select the “Receipt of Waste API changelog” link, then they go to the changelog.
  4. Given a user selects the link to field descriptions in the concentration entry, then they go to the API specification page.
  5. The page is built from docs/upcoming-changes.md and the site builds with no broken links.

Accessibility acceptance criteria

  1. The page has one H1, and the change titles are H2s with “What you need to do” and “Known issue” as H3s, with no skipped levels (1.3.1, 2.4.6).
  2. The page title is “Upcoming API changes - Defra Digital Waste Tracking Developer Guide” (2.4.2).
  3. Breaking and Non-breaking are shown in the tag text, not by colour alone (1.4.1).
  4. In forced colours mode the tag text is bold, so the tag can still be told apart from the text around it (1.4.11).
  5. The navigation link has aria-current="page" on the upcoming API changes page, which Material for MkDocs adds (4.1.2).
  6. Link text describes the destination. The links are “upcoming API changes”, “Receipt of Waste API changelog” and “Field descriptions and validation rules for concentrationOperator” (2.4.4).
  7. There is no horizontal scrolling at 320px wide or at 200% zoom (1.4.4, 1.4.10).
  8. Every function works with a keyboard, in a logical order, with the visible focus state from the site theme (2.1.1, 2.4.3, 2.4.7).

How to test

  • Run an automated check (axe or WAVE).
  • Use the page with a keyboard only.
  • Use a screen reader (NVDA or VoiceOver) to check headings and the tag text.
  • Check at 320px wide and at 200% zoom, and in a forced colours mode.

Out of scope

  • The content of future changes. The page contains the concentration threshold change as the first real entry. The breaking change and error message entries in the prototype are illustrative examples, not agreed changes.
  • Moving entries to the change log when they reach production (a process question, not a page change).
  • Letting software providers subscribe to updates.
  • Changes to the change log, which sits on the GitHub wiki.
