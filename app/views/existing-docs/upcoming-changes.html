    Upcoming API changes

    This page summarises upcoming changes to the Receipt of Waste API.

    Past changes currently live in production are listed in the Receipt of Waste API changelog.

    Report hazardous and POPs concentrations as a threshold

    Type: Non-breaking
    Status: Planned
    Test environment date: 30 November 2026
    Production environment date: January 2027 (to be confirmed)
    Affects: Receivers who accept hazardous or POPs waste

    This change allows you to report a concentration as a threshold (for example, "greater than 100 mg/kg") as well as an exact value. We've added this because users told us they often only know a limit, and the regulators support the change.

    What you need to do

    Your current integration will keep working. If your users receive hazardous or POPs waste, we recommend adding this as soon as possible, so they can report thresholds.

    To report a threshold, use the new concentrationOperator field on hazardous and POPs components in wasteItems:

    • put the number in concentration (mg/kg, greater than zero, no symbol or unit)
    • put the symbol in concentrationOperator: > for hazardous components, < or > for POPs

    Leave out concentrationOperator when you're reporting an exact value, or when concentration is null.

    Known issue

    If you send both concentration and concentrationOperator as null, you'll get a 400 response saying the concentration must be specified. Leave out concentrationOperator instead. The movement will be created with a warning that a concentration value is recommended. We'll fix this on [date / in release X].

    Require a carrier registration number

    Type: Breaking
    Status: Planned
    Test environment date: 15 December 2026
    Production environment date: February 2027 (to be confirmed)
    Affects: All software providers submitting receipt data

    This change makes the carrier registration number a required field. Requests that leave it out will be rejected. We're making it required because regulators need to identify the carrier for every movement.

    What you need to do

    Your current integration will stop working unless you update it before the production date. Send the carrier registration number with every receipt. Test your changes in the external test environment from 15 December 2026.

    Updated error message for invalid dates

    Type: Non-breaking
    Status: Planned
    Test environment date: 12 January 2027
    Production environment date: February 2027 (to be confirmed)
    Affects: Software providers who show API error messages to their users

    We're making the 400 response for an invalid date more specific. It will name the field that has the problem, for example “receiptDate must be a valid date in the format YYYY-MM-DD”. The response code does not change.

    What you need to do

    Your current integration will keep working. If you match on the text of error messages, check that your code still works with the new wording.

    Past changes currently in production appear in the Receipt of Waste API changelog.
